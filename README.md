# SnapYTube Ultimate — النسخة الاحترافية (v5.0.0)

تطوير كامل لمشروع **SnapYTube Android** (Kivy + Flask + WebView) إلى نسخة
فيها كل الميزات اللي طلبتها: إعدادات حقيقية، ثيم فاتح/داكن، اختيار جودة +
صوت فقط (MP3)، تحميل عدة روابط دفعة وحدة، كشف رابط بالحافظة تلقائياً،
"مشاركة إلى SnapYTube" من تطبيقات تانية، إشعارات أندرويد حقيقية، مشاركة
الملف المحمّل من قائمة أندرويد الأصلية، بحث بالسجل، فحص تحديثات حقيقي عن
طريق GitHub Releases، وتشخيص أخطاء. **عربي / تركي / إنجليزي كامل** بكل
شيء جديد.

> ⚠️ **بصراحة تامة قبل أي شيء:** قدرت أفحص وأشغّل كل الكود البايثون فعلياً
> بالسيرفر عندي (Flask، منطق التحميل، كل الـ API endpoints، كود الأندرويد
> الأصلي بشكل معزول) وأكدت إنه شغال صح، وصلّحت **باگين حقيقيين** كانوا
> موجودين بالأصل (قسم 2 تحت):
> 1. خط عربي وهمي كان بيكسّر التطبيق فوراً عند الفتح.
> 2. خيار إعداد بناء (`android.extra_manifest_application_arguments`) فيه
>    مشكلة موثّقة رسمياً بمستودع buildozer على GitHub ممكن تكسر البناء
>    كامل — استبدلته بآلية أضمن (p4a hook) بعد ما تحققت من الكود المصدري
>    لـ buildozer وp4a نفسهم لأتأكد من الحل.
>
> **بس ما عندي جهاز أندرويد ولا بيئة بناء APK هون**، فبناء الـ APK نفسه
> (عن طريق GitHub Actions) ما قدرت أجربه فعلياً بالتنفيذ الحقيقي — هاد
> نفس الوضع يلي كان موجود بمشروعك الأصلي أصلاً (ملاحظتك بالـ README
> القديم كانت "مش مضمون ينجح من أول محاولة ١٠٠٪"). لو طلعت أي مشكلة
> ببناء الـ CI، ابعتلي نص الخطأ بالضبط من تبويب Actions ومنصلحها فوراً.

## 1) الفكرة المعمارية (ليش هيك بنيتها؟)

التطبيق مبني من 3 طبقات، كل وحدة إلها شغلها:

```
main.py (Kivy)  →  يشغّل سيرفر Flask بالخلفية  →  يفتح WebView يعرض index.html
     │                        │                              │
  صلاحيات/إشعارات      server.py (كل الـ API)         الواجهة (HTML/CSS/JS)
  مشاركة من تطبيق ثاني  mobile_downloader.py (yt-dlp)   عربي/تركي/إنجليزي كامل
  android_native.py (الجسر لكل شيء أندرويد أصلي)
```

ليش مش Kivy UI مباشرة؟ لأنه بناء واجهة حديثة بتدعم RTL (عربي) ولغات متعددة
بـ Kivy صعب ومحدود، بينما HTML/CSS/JS عادي أسهل بكثير وأقوى بصرياً. فالحل:
Kivy بس بيشغّل خادم محلي (`127.0.0.1:5001` — ما بيطلع برا الجهاز إطلاقاً)
وبيفتحلك إياه بمتصفح WebView مدمج جوا التطبيق نفسه، تماماً متل أي تطبيق
"هجين" احترافي (نفس الفكرة يلي بيستخدمها كتير تطبيقات حقيقية بالسوق).

### هيكل الملفات

| الملف | شغلته |
|---|---|
| `main.py` | إقلاع Kivy، شاشة تحميل، صلاحيات، تشغيل Flask، فتح WebView |
| `android_native.py` | **جديد** — كل تكامل أندرويد الأصلي بمكان واحد (إشعارات، حافظة، شبكة، مشاركة) |
| `server.py` | كل الـ API (تحميل، إعدادات، ملفات، تشخيص...) |
| `mobile_downloader.py` | منطق التحميل الفعلي عن طريق yt-dlp |
| `index.html` | الواجهة الكاملة (عربي/تركي/إنجليزي، إعدادات، كل شيء مرئي) |
| `buildozer.spec` | إعدادات بناء الـ APK (صلاحيات، أرشيتكتشر، نسخ المكتبات...) |
| `intent_filters.xml` | يسجّل التطبيق بقائمة "مشاركة" بأندرويد |
| `p4a_hook.py` | **جديد** — يضيف FileProvider للمانيفست أثناء البناء (شوف قسم 2) |
| `res_xml/file_paths.xml` | أي مجلد بالضبط مسموح لـ FileProvider يشاركه |
| `.github/workflows/build.yml` | **جديد** — بناء الـ APK تلقائياً على GitHub |
| `requirements.txt` | لتجربة `server.py` على كمبيوتر عادي (بدون أندرويد) |

## 2) ثلاثة أخطاء حقيقية تم اكتشافها وإصلاحها 🐛

### أ) انهيار فوري عند الفتح (خط عربي وهمي)

شغّلت `main.py` فعلياً (بوضع اختبار بدون شاشة حقيقية) ولقيت إنه **التطبيق
كان بينهار فوراً عند الفتح** على أي جهاز ما فيه ملف خط عربي مخصص مرفق!
السبب: الكود القديم كان بيحاول يستخدم خط اسمه `"DroidSansArabic"` كـ
احتياطي، بس هاد الاسم مش خط حقيقي موجود — Kivy (عكس أدوات واجهة تانية)
لازم ملف `.ttf` فعلي موجود على القرص، مش بس اسم خط من نظام التشغيل.
النتيجة: `IOError: Label: File not found` وانهيار فوري بشاشة التحميل.

**الإصلاح:** لو ما في ملف `arabic_font.ttf` مرفق بجذر المشروع، التطبيق
هلأ بيستخدم خط Kivy الافتراضي الآمن (Roboto، موجود دايماً) ويعرض نص
شاشة التحميل *الأصلية بس* (ثانيتين قبل ما تفتح الواجهة الحقيقية) بالإنجليزي
البسيط بدل العربي. الواجهة الفعلية (`index.html`) مش متأثرة إطلاقاً —
هي أصلاً عربي/تركي/إنجليزي كامل عن طريق خطوط الويب (Google Fonts) اللي
أندرويد نفسه بيعرضها صح دايماً جوا WebView بدون أي إعداد إضافي.

**لو حابب نص عربي حقيقي حتى بشاشة التحميل الأولى نفسها:** حط أي ملف خط
يدعم العربي باسم `arabic_font.ttf` بجذر المشروع (جنب `main.py`) وبينشغل
تلقائياً — ما حطيت خط جاهز أنا لأنه ما قدرت أتأكد من ترخيصه/حجمه من بيئتي.

### ب) خطر كسر البناء كامل بسبب باگ معروف بـ buildozer/p4a

أول نسخة من هاد المشروع كانت بتعرّف `FileProvider` (المطلوب لميزة مشاركة
الملف المحمّل 🔗) عن طريق خيار `android.extra_manifest_application_arguments`
بملف `buildozer.spec`. بمراجعتي الأخيرة، دوّرت ولقيت تقرير خطأ رسمي ومفتوح
على مستودع python-for-android بـ GitHub
([رقم 2905](https://github.com/kivy/python-for-android/issues/2905))
بيوثّق بالضبط نفس المشكلة: هاد الخيار بيمرّر محتوى ملف الـ XML كـ argument
بسطر الأوامر، وفي خطأ encoding/escaping بيخلّي المحتوى يوصل لـ
`AndroidManifest.xml` بشكل تالف (علامات اقتباس مهروبة غلط) — والنتيجة
Gradle بيرفض يبني الـ APK **كامل** (مو بس ميزة المشاركة، التطبيق كله).

رحت تأكدت بنفسي من الكود المصدري لـ `buildozer` و`python-for-android`
(حمّلتهم وفحصتهم مباشرة) لقيت إنه:
- `android.extra_manifest_application_arguments` ⟵ فعلاً فيه نفس المشكلة
  (بيمرّر *محتوى* الملف كـ argument).
- `android.manifest.intent_filters` (المستخدم لميزة "مشاركة إلى SnapYTube")
  ⟵ **سليم**، لأنه بيمرّر *مسار* الملف بس، وp4a بيقرأه بنفسه بطريقة آمنة.

**الحل يلي طبّقته:** استبدلت الطريقة المكسورة بآلية "p4a hook" الرسمية
(`p4a.hook = p4a_hook.py` بـ buildozer.spec) — كود بايثون بينفّذ تلقائياً
أثناء البناء (بالضبط قبل ما Gradle يبلش) وبيضيف وسم `<provider>` مباشرة
لملف `AndroidManifest.xml` بتعديل نصي بسيط، بدون أي تمرير محتوى عبر سطر
الأوامر — فمفيش مجال للباگ إطلاقاً. جرّبت هاد المنطق فعلياً بملف مانيفست
وهمي (idempotent، وما بينهار لو الملف مفقود) وأكدت إنه شغال صح.

### ج) فشل البناء الفعلي يلي بعتلي لوگه — `flask-cors` كانت السبب 🎯

هاد الخطأ مو نظري — طلع فعلياً بتجربتك الحقيقية على GitHub Actions. فحصت
الـ log (٢٥ ميجا، ٦٠ ألف سطر) ولقيت السبب بالضبط:

```
running pip3 install blinker certifi chardet click filetype flask-cors
idna itsdangerous jinja2 markupsafe requests six urllib3 werkzeug wheel
yt-dlp --dry-run ... --only-binary=:all: --platform=android_21_arm64_v8a ...
ERROR: Could not find a version that satisfies the requirement markupsafe
(from versions: none)
```

**السلسلة الكاملة:** `flask-cors` ما إلها recipe جاهز بـ python-for-android
(عكس `flask` نفسها يلي إلها recipe مخصص). فلمّا p4a بيحاول يحمّلها، بيسلّمها
لـ pip العادي. pip (يلي ما بيعرف إصلاً إنه Flask عندها recipe جاهزة من جهة
تانية) بيحاول يحل متطلبات flask-cors كاملة من PyPI عادي — واللي بتتطلب
`Flask` ← `Jinja2` ← `MarkupSafe`. وMarkupSafe فيها جزء C (C extension)
فمالهاش "wheel" جاهز لمعمارية أندرويد على PyPI (ولا حتى بتتوقع حد ينشر
وحدة) — و`--only-binary=:all:` بتمنع أي محاولة بناء من المصدر كـ بديل.
النتيجة: فشل، والبناء كامل بيوقف.

**تأكدت من التشخيص عملياً:** حمّلت كود `buildozer` و`python-for-android`
المصدري بنفسي وتتبعت بالضبط وين بينولّد هاد الأمر (`process_python_modules`
بملف `build.py`)، وأكّدت إنه `flask` لحالها (بدون flask-cors) ما بتدخل
هالمسار إطلاقاً لأنها معروفة كـ recipe. بعدين حذفت flask-cors فعلياً من
بيئتي المحلية وشغّلت `server.py` بدونها بالكامل — اشتغل تمام 100%.

**الحل:** حذفت `flask-cors` نهائياً (مش ضرورية أصلاً — الواجهة وكل الـ API
بنفس العنوان تماماً `127.0.0.1:5001` دايماً، فمافي "طلب عابر للأصول" حقيقي
بهالبنية) وضفت بدالها هيدر CORS بسيط يدوي بـ `server.py` (بدون أي مكتبة
خارجية). كمان حذفت `werkzeug` من قائمة المتطلبات الرئيسية لأنها أصلاً
بتنجيب تلقائياً عن طريق recipe الـ flask نفسها (`python_depends`)، وتكرار
ذكرها كان زيادة سطح مخاطرة بدون أي فايدة حقيقية.

## 3) كل ميزة جديدة — شرح العملية + أخطاء محتملة

### ⚙️ الإعدادات
زر الترس (أعلى يسار الشاشة) بيفتح لوحة فيها: اللغة، الوضع الداكن/الفاتح،
الجودة الافتراضية، "واي فاي فقط"، كشف الحافظة التلقائي، وقسم تشخيص.
كل إعداد بينحفظ فوراً بملف `settings.json` داخل مجلد التطبيق (مش بالمتصفح
فقط) عشان يضل محفوظ حتى لو أقفلت التطبيق كامل.
**خطأ محتمل:** لو ملف `settings.json` انكسر/تلف بأي شكل، الكود بيرجع
تلقائياً للقيم الافتراضية بصمت (ما بينهار التطبيق) — جرّبت هاد السيناريو
فعلياً وأكدته.

### 🌗 الوضع الداكن/الفاتح
تبديل فوري عن طريق متغيرات CSS. **ملاحظة صادقة:** غطّيت العناصر الأساسية
(الخلفية، البطاقات، النصوص، الحقول)؛ بعض التفاصيل الزخرفية الصغيرة جداً
(ظل لوني على زر معين مثلاً) ممكن تضل بنفس الطابع بالوضعين — تحسين بصري
بسيط ممكن أعمله لاحقاً لو حبيت.

### 🎚️ اختيار الجودة + صوت فقط (MP3)
قائمة منسدلة فوق زر التحميل: تلقائي / 4K / 1080 / 720 / 480 / 360 / صوت
فقط. لو `ffmpeg` متوفر (شوف قسم ffmpeg تحت)، بيحوّل الصوت لـ MP3 فعلياً
ويدمج فيديو+صوت لأي جودة مختارة. **بدون ffmpeg:** التحميل لسا بيشتغل، بس
بيضطر ياخد صيغة جاهزة من المصدر (بدون تحويل MP3 حقيقي) — بيوضحلك هاد
بالنتيجة مباشرة ("تم الحفظ بصيغة الصوت الأصلية").

### 📥 تحميل عدة روابط دفعة وحدة (Batch)
مفتاح بجانب خانة الرابط يبدّلها لمربع نص (رابط بكل سطر). المعالجة
**متتالية مو متوازية** عمداً — عشان ما نرهق معالج/بطارية الموبايل بعدة
تحميلات بنفس اللحظة. كل رابط بيظهر بقائمة بحالته (بالانتظار/جاري/تم/فشل).

### 📋 كشف رابط بالحافظة
كل 3 ثواني (لو الإعداد مفعّل) بيفحص الحافظة؛ لو لقى رابط من منصة مدعومة
وما كان ظهر قبل هيك، بيعرض شريط صغير فيه زر "لصق". ما بيلصق تلقائياً —
دايماً بانتظار موافقتك.

### 📤 "مشاركة إلى SnapYTube" (استقبال من تطبيق ثاني)
من يوتيوب/تيك توك/أي تطبيق، اضغط "مشاركة" واختر SnapYTube — الرابط
بيترجع تلقائياً جوا التطبيق (حتى لو كان شغال بالخلفية أصلاً). تقنياً:
intent-filter بـ `intent_filters.xml` + قراءة الـ Intent بـ
`android_native.py`. **هاي من أكتر الميزات تعقيداً تقنياً بكل المشروع** —
لو ما ظهرش SnapYTube بقائمة المشاركة بعد التثبيت، أو ظهر بس الرابط ما
وصل، ابعتلي وصف المشكلة بالضبط.

### 🔔 إشعارات أندرويد حقيقية
إشعار بشريط تقدّم أثناء التحميل + إشعار اكتمال/فشل. من أندرويد 13
(API 33) هاد يحتاج صلاحية `POST_NOTIFICATIONS` تُطلب تلقائياً عند أول
فتح للتطبيق. **لو رفضت الصلاحية من نافذة النظام**، التحميل بيشتغل عادي
بس بدون إشعارات — مش خطأ قاتل.

### 🔗 مشاركة الملف المحمّل (Share Sheet أصلية)
زر المشاركة 🔗 بجانب كل فيديو بالسجل بيفتح قائمة أندرويد الأصلية
(واتساب، تيليغرام، بلوتوث...). يحتاج `FileProvider` (معرّف بملفين XML
جديدين) لأنه أندرويد 7+ بيمنع مشاركة ملف مباشر بين تطبيقات بدون هيك.
**هاي كمان من الميزات التقنية المعقدة** وما قدرت أجربها على جهاز حقيقي.

### 🔍 بحث بالسجل والملفات
خانة بحث بسيطة فوق كل قائمة، بتفلتر بالاسم فوراً وبالطرفين (مو استدعاء
سيرفر إضافي).

### 🔄 فحص تحديثات حقيقي
بيسأل GitHub Releases API فعلياً عن آخر إصدار منشور بمستودعك، ويقارنه
برقم الإصدار الحالي (`APP_VERSION` بـ `server.py`). لازم تنشر "Release"
بـ GitHub (الـ workflow الجديد بيعمل هاد تلقائياً لو دفعت تاغ `v5.0.0`
مثلاً) عشان يكون في شي يقارن فيه.

### 🩺 تشخيص (بقسم الإعدادات)
بيعرض: حالة الشبكة الحالية (واي فاي/بيانات/غير متصل)، هل `ffmpeg`
متوفر، رقم إصدار التطبيق. مفيد لما تبعتلي "في مشكلة" — بعتلي سكرين شوت
من هاد القسم كبداية.

## 4) حذف ملف (Delete)
بدل نافذة تأكيد النظام (`confirm()`) اللي **مش مضمونة تشتغل بأي WebView
أندرويد بدون كود جافا إضافي معقّد**، استخدمت طريقة "اضغط مرتين للتأكيد":
ضغطة أولى على 🗑️ بتحوّلها لعلامة ✓ لمدة 3 ثواني، وضغطة تانية بهاي الفترة
بتنفّذ الحذف فعلياً. أبسط وأضمن 100% من نافذة نظام غير مضمونة.

## 5) خطوات البناء (نفس الطريقة القديمة بالضبط)

1. ادفع كل محتوى هاد المجلد لمستودعك على GitHub (أو مستودع جديد):
   ```bash
   git add .
   git commit -m "SnapYTube Pro v5.0.0 — إعدادات، ثيم، مشاركة، إشعارات..."
   git push
   ```
2. روح لتبويب **Actions** بصفحة المستودع — البناء بيبلش تلقائياً (أو اضغط
   "Run workflow" يدوياً).
3. انتظر 10-20 دقيقة (أول مرة أطول لأنه بيحمّل Android SDK/NDK كامل).
4. افتح التشغيلة (run) ونزّل `snapytube-apk` من قسم **Artifacts** بالأسفل.
5. **لإصدار رسمي مع فحص تحديثات شغال:** بعد التأكد إنه كل شيء تمام:
   ```bash
   git tag v5.0.0
   git push --tags
   ```
   هاد بينشئ "Release" رسمي بـ GitHub مع الـ APK مرفق — وهاد بالضبط
   اللي ميزة "التحقق من التحديثات" جوا التطبيق بتفحصه.

### تجربة سريعة بدون أندرويد (اختياري، قبل ما تبني APK)
```bash
pip install -r requirements.txt
python3 -c "import server; server.build_app('./local_data').run(host='127.0.0.1', port=5001)"
# افتح http://127.0.0.1:5001 بأي متصفح
```
هيك بتتأكد إنه الواجهة ومنطق التحميل شغالين صح قبل ما تستثمر وقت ببناء
APK كامل. (ميزات أندرويد الأصلية طبعاً ما رح تشتغل هون، بس ما رح تسبب
أي خطأ — بترجع قيم افتراضية آمنة تلقائياً.)

## 6) جدول أخطاء شائعة بالبناء (CI) وحلولها

| الخطأ | السبب الأرجح | الحل |
|---|---|---|
| `Failed to install the following Android SDK packages` | أول بناء، تحميل SDK انقطع | أعد تشغيل الـ workflow (Re-run jobs) |
| `AAPT: error: resource xml/file_paths not found` | خطأ بمسار `android.res_xml` بـ buildozer.spec | تأكد إنه `res_xml/file_paths.xml` موجود بنفس المسار المكتوب |
| فشل بخطوة "Create GitHub Release" | التاغ مش بصيغة `v...` أو already exists | احذف التاغ القديم (`git tag -d vX && git push --delete origin vX`) وأعد الدفع |
| SnapYTube ما بيظهر بقائمة "مشاركة" بعد التثبيت | أندرويد أحياناً بياخد وقت يحدّث الفهرس، أو `intent_filters.xml` ما انضاف صح | أعد تشغيل الجهاز، أو افحص AndroidManifest الناتج داخل الـ APK |
| الإشعارات ما بتظهر إطلاقاً | رفضت صلاحية الإشعارات، أو الجهاز أندرويد أقدم من 8 (مافي قنوات إشعار) | افحص إعدادات التطبيق بالنظام → إشعارات |
| زر المشاركة 🔗 ما بيفتح شي | مشكلة بتوافق authority الـ FileProvider | ابعتلي نص الخطأ من قسم "تشخيص" بالإعدادات |
| `Element type "application" must be followed by...` أو أي خطأ XML بالمانيفست | لو ظهر هاد رغم إصلاح قسم 2-ب، معناها `p4a_hook.py` ما اشتغل | دوّر بلوگ البناء عن سطر يبلش بـ `[p4a_hook]` وابعتهولي بالضبط |
| `Could not find a version that satisfies the requirement markupsafe/jinja2/click...` | باگ flask-cors (شوف قسم 2-ج) — لازم يكون مصلّح بهاي النسخة | لو ظهر برضو، ابعتلي أي اسم حزمة تانية ظهرت بنفس الرسالة |

لأي خطأ مو بالجدول: انسخ النص الكامل الأحمر من الـ log وابعتهولي، منحله
سوا تماماً متل ما صار بكل الجلسات السابقة.

## 7) ملاحظات أمان (مرعية بكل الكود الجديد)
- السيرفر على `127.0.0.1` بس — ما بيطلع برا الجهاز إطلاقاً لأي شبكة.
- كل مسار بيتعامل مع اسم ملف (`/api/video`, `/api/delete`, `/api/share`)
  بيتحقق إنه المسار الحقيقي (`realpath`) لسا جوا مجلد التحميلات بالضبط —
  يمنع هجوم "Path Traversal" (مثل `../../etc/passwd`). مجرّب فعلياً.
- تحديد معدّل طلبات (Rate Limiting) بسيط على التحميل (12 طلب/دقيقة) يمنع
  إغراق السيرفر المحلي بالخطأ.
- `FileProvider` بيكشف **مجلد `downloads/` بس**، مش كل تخزين التطبيق.
- ملف الإعدادات JSON عادي بدون أي بيانات حساسة (لا كلمات سر، لا مفاتيح).

## 8) لو غيّرت اسم الحزمة أو المستودع
لو غيّرت `package.domain`/`package.name` بـ `buildozer.spec`، لازم تحدّث
نفس قيمة الـ authority بمكانين إضافيين يدوياً (لازم تكون متطابقة تماماً
بالثلاثة أماكن):
1. `FILE_PROVIDER_AUTHORITY` بملف `p4a_hook.py`
2. `FILE_PROVIDER_AUTHORITY` بملف `android_native.py`

ولو غيّرت اسم مستودع GitHub، حدّث `UPDATE_CHECK_REPO` بأعلى `server.py`.
